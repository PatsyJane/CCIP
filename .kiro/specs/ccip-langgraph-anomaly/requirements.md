# Requirements Document: CCIP LangGraph Anomaly Detection Workflow

## Introduction

This feature replaces the previous linear Cost Anomaly Alerting pipeline
(`cost-anomaly-alerting`) with the **CCIP Archi-3 workflow**: a stateful,
graph-orchestrated cloud cost anomaly detector. It uses **LangGraph** for state
management and conditional routing across six execution phases, performs
**account-level** anomaly detection using **RobustSTL/STL** seasonal-trend
decomposition (via `statsmodels`), maintains a **persistent JSON metadata store**
of known services and prior anomalies, and dispatches a **consolidated email
alert** whose narrative is generated by the **Gemini LLM**.

The workflow consumes cloud cost data through the existing **FastMCP Connector**
and its AWS CUR Cost_Tool (`aws_cur_cost`), which is preserved unchanged. All
structural thresholds and statistical parameters live in a `config.yaml` file;
sensitive and environment-specific values are injected from a local `.env` file
at load time using a `${VAR_NAME}` syntax wrapper.

### Scope

| Concern | Status |
| --- | --- |
| LangGraph orchestration of six phases + two conditional routers | **In scope** |
| Four-mode data-depth classification (Cold Start / Initial / Beginner / Normal) | **In scope** |
| MCP-based ingestion of account-total and service-level daily costs | **In scope** |
| Persistent JSON metadata store (known services, seasonal context, last anomaly) | **In scope** |
| RobustSTL/STL decomposition and residual-based account anomaly detection | **In scope** |
| Cold-start absolute-threshold detection | **In scope** |
| New-service detection as an independent alert trigger | **In scope** |
| Service-level drill-down and contributor isolation | **In scope** |
| Gemini-generated email narrative + SMTP dispatch | **In scope** |
| `config.yaml` with `${VAR}` injection from `.env` | **In scope** |
| Structured-error handling reusing `connector.errors` | **In scope** |
| AWS only (POC); GCP / Azure | **Deferred** |
| Automated remediation; multi-account batch scheduling | **Deferred** |
| Database-backed metadata (beyond a single JSON file) | **Deferred** |

### Preserved from the existing codebase

- The entire FastMCP Connector: `server.py`, `config.py`, `http_client.py`,
  `validation.py`, `dimensions.py`, `numeric.py`, `response_adapter.py`,
  `tools/aws_cur_cost.py`.
- The shared error contract `connector.errors.structured_error` and the
  `ErrorCategory` enum (`missing-data`, `unreachable-source`,
  `invalid-parameter`, `unexpected-error`).

### Replaced / discarded

- The entire `src/connector/anomaly/` package and `tests/anomaly/` suite are
  discarded; no fallback is retained.

### Glossary

- **Workflow / Graph** — the LangGraph `StateGraph` orchestrating the six nodes.
- **Node / Phase** — one execution step in the graph (Phases 1–6).
- **Graph_State** — the shared, typed state object passed between nodes.
- **Data_Mode** — the account's history-depth classification: `Cold Start`
  (< 30 complete days), `Initial` (30–59), `Beginner` (60–89), `Normal` (≥ 90).
- **Target_Date** — the evaluation date, supplied manually for a run.
- **Metadata_Store** — the single persistent JSON file holding
  `known_active_services`, seasonal context, and last-anomaly records.
- **New_Service** — a service observed on the Target_Date that is absent from the
  Metadata_Store's known services.
- **Account_Anomaly** — a detected spike in the account-level total cost.
- **Anomaly_Contributor** — a service identified as driving an Account_Anomaly.
- **Structured_Error** — the shared `{"error", "category", ...}` failure object.

## Requirements

### Requirement 1: Configuration loading with .env injection

**User Story:** As an operator, I want all thresholds and model parameters in a
`config.yaml` with secrets injected from `.env`, so that I can tune the workflow
without editing code and without committing secrets.

#### Acceptance Criteria

1. WHEN the workflow loads configuration THEN the system SHALL read a
   `config.yaml` file containing structural thresholds, RobustSTL/STL parameters,
   and workflow toggles.
2. WHEN a `config.yaml` value contains a `${VAR_NAME}` placeholder THEN the system
   SHALL substitute the value of `VAR_NAME` from the process environment (loaded
   from `.env` via `python-dotenv`) before parsing the value.
3. IF a referenced `${VAR_NAME}` is absent or blank in the environment AND the
   setting is required THEN the system SHALL raise a `ConfigError` naming the
   missing variable and abort the run.
4. WHEN configuration is loaded THEN the resulting config object SHALL be
   immutable and SHALL expose, at minimum: the cold-start absolute threshold
   (default `$20`), the statistical-threshold method (`iqr` with factor `1.5`, or
   `sigma` with factor `3`), the STL period/seasonal parameters, the LLM model id,
   the email from/to addresses, and the Metadata_Store file path.
5. WHEN secret values (LLM API key, SMTP password) are loaded THEN the config
   object SHALL store them on a `repr`-excluded field whose `__repr__` is redacted,
   so secret values never appear in logs, `repr`, or node output.
6. IF `config.yaml` is missing, unreadable, or not valid YAML THEN the system
   SHALL raise a `ConfigError` identifying the file and the reason.

### Requirement 2: Graph state and run initialization

**User Story:** As a developer, I want a well-defined shared state object, so that
each node reads and writes a predictable, typed structure.

#### Acceptance Criteria

1. WHEN a run begins THEN the system SHALL initialize a Graph_State seeded with
   the supplied `account_id` and `target_date` (`YYYY-MM-DD`).
2. WHEN a run begins THEN the Graph_State SHALL define these keys with safe
   defaults: `data_mode`, `account_total_cost`, `service_costs`, `metadata`,
   `new_services_detected` (empty list), `account_anomaly_detected` (`False`),
   `anomaly_contributors` (empty list), and `alert_payload` (empty/none).
3. IF `account_id` is missing/blank or `target_date` is not a valid
   `YYYY-MM-DD` calendar date THEN the system SHALL return an `invalid-parameter`
   Structured_Error naming the offending input and SHALL NOT execute any node.
4. WHEN the graph is constructed THEN the entry edge SHALL route `START` to the
   `determine_data_mode` node (Phase 1).

### Requirement 3: Phase 1 — Determine data mode

**User Story:** As an analyst, I want the account's history depth classified, so
that detection uses the correct method for the available data.

#### Acceptance Criteria

1. WHEN `determine_data_mode` runs THEN the system SHALL perform the single MCP
   AWS CUR Cost_Tool fetch for the run — one `DAILY` request over the maximum
   historical window (90 days up to and including the Target_Date) — and SHALL
   store the raw fetched payload on the Graph_State for Phase 2 to normalize, so
   that no second MCP call is made.
2. WHEN the raw payload is fetched THEN the system SHALL count the available
   historical complete days up to the Target_Date and SHALL set `data_mode` to
   `Cold Start` if `< 30` days, `Initial` if `30`–`59`, `Beginner` if `60`–`89`,
   and `Normal` if `>= 90`.
3. IF the Cost_Tool returns a Structured_Error THEN the node SHALL return a
   Structured_Error preserving its `category`, naming the ingestion/data-mode
   phase as the source, and SHALL halt the workflow.
4. IF the Cost_Tool returns a non-`DAILY` granularity THEN the node SHALL return an
   `invalid-parameter` Structured_Error naming the unexpected granularity.
5. IF the fetched payload yields no cost data THEN the node SHALL return a
   `missing-data` Structured_Error and SHALL halt the workflow.
6. WHEN the data mode is set THEN the node SHALL route to `ingest_daily_data`
   (Phase 2).

### Requirement 4: Phase 2 — Normalize ingested data

**User Story:** As an analyst, I want the raw fetched payload normalized into the
account total and per-service costs, so that detection and drill-down have a clean
standardized structure — without a second network call.

#### Acceptance Criteria

1. WHEN `ingest_daily_data` runs THEN the system SHALL read the raw payload stored
   by Phase 1 from the Graph_State and SHALL NOT perform any additional MCP call.
2. WHEN the raw payload is normalized THEN the system SHALL set
   `account_total_cost` (the Target_Date total, a float), `service_costs` (a
   structure keyed by service name for the Target_Date), `history_series` (the
   account total per day, ascending), and `service_history` (per-service daily
   series).
3. IF the raw payload is absent or malformed in the Graph_State THEN the node
   SHALL return an `unexpected-error` Structured_Error naming the ingestion phase.
4. IF normalization yields zero service costs for the Target_Date THEN the node
   SHALL treat the Target_Date account total as `0.00` (imputed) rather than
   failing, so the account check and new-service check can still run.
5. IF the Target_Date yields no cost data THEN the node SHALL return a
   `missing-data` Structured_Error and SHALL halt the workflow.
6. WHEN ingestion succeeds THEN the node SHALL route to
   `update_metadata_and_model` (Phase 3).

### Requirement 5: Phase 3 — Update metadata and model

**User Story:** As an analyst, I want known services tracked and the seasonal
model refreshed, so that new services are recognized and the baseline reflects
history.

#### Acceptance Criteria

1. WHEN `update_metadata_and_model` runs THEN the system SHALL load the
   Metadata_Store JSON (creating an empty store on first run) and expose it on
   `metadata`.
2. WHEN today's ingested services are compared against the stored
   `known_active_services` THEN the system SHALL append any service not previously
   known to `new_services_detected`.
3. WHEN new services are detected THEN the system SHALL immediately add them to the
   Metadata_Store so they are recognized in subsequent runs.
4. IF `data_mode` is greater than `Cold Start` (i.e. `>= 30` complete days) THEN
   the system SHALL execute RobustSTL/STL on the account-level historical series up
   to the Target_Date to compute Trend, Seasonality, and Residual components.
5. WHEN the model is computed THEN the system SHALL persist the revised seasonal
   multipliers and/or moving averages to the Metadata_Store.
6. WHEN metadata and model updates complete THEN the node SHALL route to
   `detect_account_anomaly` (Phase 4).
7. IF the Metadata_Store file is present but unreadable or not valid JSON THEN the
   node SHALL return an `unexpected-error` Structured_Error identifying the file.
8. WHEN the Metadata_Store is written THEN the write SHALL be atomic (write-to-temp
   then replace) so a crash cannot corrupt the store.

### Requirement 6: Phase 4 — Detect account anomaly

**User Story:** As an analyst, I want the account total checked for an anomaly
using the method appropriate to the data mode, so that detection is reliable at
every history depth.

#### Acceptance Criteria

1. WHEN `detect_account_anomaly` runs THEN the system SHALL load the detection
   thresholds from the configuration.
2. IF `data_mode` is `Cold Start` THEN the system SHALL compare the Target_Date
   `account_total_cost` against the most recent previous non-anomaly day's total
   and SHALL set `account_anomaly_detected = True` if the absolute difference
   exceeds the configured absolute threshold (default `$20`).
3. IF `data_mode` is `Initial`, `Beginner`, or `Normal` THEN the system SHALL
   compute the residual of the Target_Date cost from the STL model and SHALL set
   `account_anomaly_detected = True` if the residual exceeds the configured
   statistical threshold (`Q3 + 1.5 × IQR` or `3σ`, per config).
4. WHEN detection completes THEN the system SHALL set `account_anomaly_detected`
   (boolean) in the Graph_State.
5. WHEN detection completes THEN the node SHALL route to the Anomaly-Check
   conditional router.
6. IF there is no prior non-anomaly day available for a `Cold Start` comparison
   THEN the system SHALL treat the account as not anomalous for the account check
   (deferring to the new-service trigger) and SHALL record that no baseline day was
   available.

### Requirement 7: Conditional routing — anomaly check and alert check

**User Story:** As a developer, I want the graph to branch on detection results,
so that drill-down and alerting run only when warranted.

#### Acceptance Criteria

1. WHEN the Anomaly-Check router evaluates AND `account_anomaly_detected == True`
   THEN the graph SHALL route to `drill_down_services` (Phase 5).
2. WHEN the Anomaly-Check router evaluates AND `account_anomaly_detected == False`
   THEN the graph SHALL route directly to the Alert-Check router, skipping
   drill-down.
3. WHEN the Alert-Check router evaluates AND (`account_anomaly_detected == True`
   OR `new_services_detected` is non-empty) THEN the graph SHALL route to
   `dispatch_alerts` (Phase 6).
4. WHEN the Alert-Check router evaluates AND neither condition holds THEN the graph
   SHALL route to `END` with no alert dispatched.
5. WHEN `drill_down_services` completes THEN it SHALL route to the Alert-Check
   router.
6. WHEN `dispatch_alerts` completes THEN it SHALL route to `END`.

### Requirement 8: Phase 5 — Drill down services

**User Story:** As an analyst, I want the services driving a spike isolated and put
in seasonal context, so that the alert tells me where the money went.

#### Acceptance Criteria

1. WHEN `drill_down_services` runs THEN it SHALL execute only if
   `account_anomaly_detected == True`.
2. WHEN drill-down runs THEN the system SHALL compare the Target_Date service-level
   costs against the most recent previous non-anomaly day's service costs.
3. WHEN per-service deltas are computed THEN the system SHALL isolate the services
   responsible for the increase and populate `anomaly_contributors` with each
   service name and its delta amount.
4. WHEN a contributor spike aligns with stored seasonal context (e.g. a known
   "1st of the month" pattern) THEN the system SHALL annotate the contributor with
   that seasonal context.
5. WHEN drill-down completes THEN it SHALL route to the Alert-Check router.

### Requirement 9: Phase 6 — Dispatch alerts (narrative + delivery)

**User Story:** As a stakeholder, I want one consolidated, well-explained email
when something material happens, so that I can act without reading raw numbers.

#### Acceptance Criteria

1. WHEN `dispatch_alerts` runs THEN it SHALL execute only if
   `account_anomaly_detected == True` OR `new_services_detected` is non-empty.
2. WHEN building the alert THEN the system SHALL fetch the last-known-anomaly
   record (date and resolution/context) for the account from the Metadata_Store.
3. WHEN constructing the payload THEN the system SHALL include: (a) the account's
   current `data_mode`; (b) details of newly detected services, if any; (c) the
   primary `anomaly_contributors` with their delta and seasonal context, if an
   anomaly was detected; and (d) the date and context of the last recorded anomaly.
4. WHEN the alert narrative is generated THEN the system SHALL use the Gemini LLM
   to render a human-readable explanation from the deterministically computed
   payload, and the LLM SHALL NOT alter, recompute, or invent any numeric value.
5. WHEN the narrative is ready THEN the system SHALL deliver the alert via SMTP; IF
   SMTP is not fully configured THEN the system SHALL perform a safe dry run
   (log the rendered alert, send nothing) and complete without raising.
6. IF the LLM is unreachable or exceeds its timeout THEN the system SHALL fall back
   to a deterministic templated narrative rather than failing the whole run, and
   SHALL record that the narrative was templated.
7. WHEN an anomaly was dispatched THEN the system SHALL record this run's anomaly
   (date, contributors, context) as the new last-known-anomaly in the
   Metadata_Store.
8. WHEN delivery (or dry run) completes THEN the node SHALL set `alert_payload` in
   the Graph_State and route to `END`.

### Requirement 10: Error handling and totality

**User Story:** As an operator, I want the workflow to fail safely and
informatively, so that one bad run never crashes or corrupts state.

#### Acceptance Criteria

1. WHEN any node encounters a failure THEN it SHALL return a Structured_Error built
   with `connector.errors.structured_error` carrying a category from the shared
   `ErrorCategory` enum, rather than raising across the node boundary.
2. WHEN a node returns a Structured_Error THEN the graph SHALL stop executing
   further detection/alerting work and SHALL surface the error unchanged as the run
   result.
3. WHEN any unhandled exception occurs within a node THEN it SHALL be mapped to an
   `unexpected-error` Structured_Error with a non-empty message of at most 500
   characters and SHALL NOT leak secrets.
4. WHEN any Structured_Error is produced THEN every configured secret substring
   SHALL be scrubbed from all of its fields before it leaves the workflow.
5. WHEN the Metadata_Store write fails THEN the system SHALL surface an
   `unexpected-error` and SHALL NOT leave the store partially written (atomic
   write, per Requirement 5.8).

### Requirement 11: Observability of the run outcome

**User Story:** As an operator running the CLI, I want to see exactly what the
workflow decided and did, so that I can trust and debug it.

#### Acceptance Criteria

1. WHEN a run completes THEN the system SHALL report the final `data_mode`,
   whether an account anomaly was detected, the list of new services, the anomaly
   contributors, and whether an alert was dispatched (or dry-run).
2. WHEN a run ends in a Structured_Error THEN the system SHALL report the error's
   message and category and SHALL exit with a non-zero status in the CLI.
3. WHEN a run completes successfully THEN the system SHALL exit zero in the CLI.
4. WHEN the workflow reports results THEN it SHALL report only what the nodes
   actually produced and SHALL fabricate nothing.
